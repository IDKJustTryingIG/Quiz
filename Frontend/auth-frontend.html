Logging in, signing up, logging out and refreshing all travel the same path through the same four files. Once you can see the path, each flow is just a different stop along it.

The code behind each layer

Transport — the only place fetch appears

Every call sets credentials: "include". Without it the browser leaves the refresh cookie behind and the server cannot tell who is calling.

src/lib/api.ts 
const send = (path, options = {}) => {
  const headers = {};
  if (options.body !== undefined) headers["Content-Type"] = "application/json";
  if (accessToken) headers.Authorization = `Bearer ${accessToken}`;

  return fetch(apiUrl(path), {
    method: options.method ?? "GET",
    headers,
    credentials: "include",   // sends the refresh cookie
    body: options.body === undefined ? undefined : JSON.stringify(options.body),
  });
};

Requests — signup and login are the same shape

Since your backend changed, creating an account returns exactly what logging in returns: an access token in the body, a refresh cookie in the headers. So both go through one helper rather than two near-identical copies.

src/lib/authApi.ts 
const startSession = async (path, body) => {
  const tokens = await apiRequest(path, { method: "POST", body, noRetry: true });
  readTokens(tokens);          // keep the access token in memory
  return tokens;
};

export const signUpRequest = (input) => startSession("/api/auth/signup", input);
export const loginRequest = (email, password) =>
  startSession("/api/auth/login", { email, password });

noRetry is the interesting flag. Everywhere else, a rejection means the token went stale and is worth retrying after a refresh. Here it means the email or password was wrong, and retrying would only be told the same thing again.

Session — the only place React state lives

src/lib/auth.tsx 
/** Fetch the profile and mark the app signed in. */
const adopt = useCallback(async () => {
  const profile = await meRequest();
  setUser(profile);
  setStatus("authenticated");
}, []);

const login = async (email, password) => { await loginRequest(email, password); await adopt(); };
const signUp = async (input)          => { await signUpRequest(input);        await adopt(); };

Two calls, not one, because the token says almost nothing about you — a user id, a jti, an email claim. The username and picture the interface renders come from /api/auth/me.

Three states, and why the first one matters

The whole app reads one value: status. It starts as loading, and that is not a detail — it is the difference between working and infuriating.

Refresh, and why only one at a time

The access token lasts fifteen minutes. When it runs out, the next call comes back 401 and the transport quietly fixes it: get a new token, run the request again. The screen never finds out.

src/lib/api.ts 
let response = await send(path, options);

if (response.status === 401 && !options.noRetry) {
  const refreshed = await refreshSession();
  if (refreshed) response = await send(path, options);
}

Now suppose three calls expire together. Run it both ways.

Three calls, all holding a token that just expired.
The server swaps the refresh token for a new one every time it is used. So the second and third callers turn up holding a token that has already been spent, which looks exactly like a stolen one being replayed — and the server signs you out everywhere. Sharing one refresh is what prevents that.

What the two forms share

Login and signup need the same three things: a busy flag, a message when it fails, and per-field messages when the server says which field was wrong. That lives in one hook.

src/lib/authForm.ts 
const { pending, error, fieldErrors, run } = useAuthSubmit();

// run() returns true if it worked, so the page decides where to go next
const ok = await run(() => login(email, password), (cause) =>
  cause.status === 401
    ? "That email and password do not match an account."
    : cause.message);

if (ok) navigate(from, { replace: true });

Why the wording is rewritten

The server answers a bad login vaguely on purpose, so nobody can use the login form to find out which email addresses have accounts. That is right for the API and useless on screen, so the page supplies a human sentence.

Why field errors hide the banner

When the server names the fields that were wrong, those messages already sit under the inputs. A banner repeating them adds nothing, so it only appears when there are no field messages to show.
